# Инженерные принципы

Это не skill и не список команд — команды и правила инструментов см. в `CLAUDE.md`, порядок браузерной проверки — в `.claude/skills/browser-verification/SKILL.md`. Здесь описано, как в этом проекте принимаются решения и оценивается качество результата, на трёх этапах: Design → Implementation → Verification.

## Design

При проектировании интерфейса учитывать:

- задачу пользователя — что человек пытается сделать на этом экране/секции;
- визуальную иерархию — что должно быть замечено первым;
- читаемость — контраст, размер текста, длина строки;
- консистентность — с уже существующей дизайн-системой проекта (`src/app/styles/tokens.scss`, `src/shared/ui/`), не изобретать параллельный стиль;
- адаптивность — поведение на мобильных и десктопе;
- accessibility — семантика, фокус, доступные формы, клавиатурная навигация;
- состояния — loading, empty, error, success, disabled — по умолчанию, не только «счастливый путь»;
- целесообразность каждого визуального решения — если анимацию/эффект нельзя объяснить одним предложением зачем он нужен, скорее всего он не нужен;
- отсутствие типичного шаблонного «AI-дизайна» — лишней декоративности, случайных градиентов и теней без функции.

Если в проекте установлен и подходящий design/UI-skill — можно им воспользоваться, но ни один сторонний skill не обязателен и не должен считаться недостающим, если его нет: не притворяться, что он был вызван, если это не так.

## Implementation

При реализации:

- сначала разобраться в задаче и ограничениях, прежде чем писать код;
- использовать существующие компоненты и паттерны проекта, а не писать заново;
- выбирать самое простое решение, которого достаточно для задачи;
- не добавлять архитектурную сложность ради демонстрации технологии;
- чётко разделять ответственность между компонентами — один компонент, одна причина для изменения;
- писать понятные типы и названия, отражающие домен, а не техническую реализацию;
- явно закладывать состояния интерфейса и обработку ошибок, а не только основной сценарий;
- не ухудшать производительность и доступность ради визуального эффекта;
- избегать преждевременных абстракций — три похожих места лучше, чем неверно угаданная общая абстракция;
- оставлять решение удобным для последующих изменений, не проектируя одноразовый код.

## Verification

Перед тем как считать задачу завершённой:

- проверить соответствие исходным требованиям задачи;
- прогнать typecheck и lint;
- запустить релевантные тесты;
- проверить обработку основных состояний интерфейса (не только happy path);
- оценить accessibility (семантика, фокус, контраст) там, где менялся UI;
- проверить визуальный результат в браузере — но только если UI действительно менялся (см. `.claude/skills/browser-verification/SKILL.md` для решения, как именно);
- провести самопроверку кода (self-review) перед тем как считать готовым;
- явно указать, какие ограничения остались или какие части не были проверены — не замалчивать;
- не заявлять об успешном прохождении проверки, если соответствующая команда или инструмент фактически не запускались.
